# Architecture

LEGAL MASTER uses a modular monolith to keep local development simple while preserving explicit boundaries.

```text
React UI -> FastAPI API -> application modules -> PostgreSQL
                                     |         -> private document storage
                                     |         -> Redis (future jobs)
                                     |         -> Qdrant (future vectors)
                                     `---------> provider interfaces (future AI)
```

## Boundary rules

- API routers validate transport data and delegate work; they do not perform storage or database operations directly.
- Services coordinate use cases, repositories own SQLAlchemy queries, and models remain persistence-focused.
- Every workspace-scoped query must include workspace authorization. Future vector payloads must carry workspace, case, document, version, and page identifiers so retrieval can enforce the same boundary.
- Storage keys are generated by the application. Original filenames are metadata only and never become filesystem paths.
- AI, extraction, OCR, chunking, storage, and vector integrations depend on internal interfaces. Provider-specific clients stay at the boundary.
- Background processing remains part of the same codebase and transaction model; Redis-backed workers can be added when ingestion arrives.

### Authentication boundary

Phase 2 authentication uses Argon2id password hashes and two JWT types. Short-lived access tokens are stateless bearer credentials. Refresh tokens are rotated on every use; their `jti` values are stored in PostgreSQL so logout, expiration, and reuse can be enforced without storing raw token material. Browser refresh tokens use an HttpOnly cookie while access tokens remain in memory.

### Workspace and document authorization boundary

The tenant chain is `Document -> Case -> Workspace -> WorkspaceMember -> User`. `get_workspace_access` resolves a workspace only through the authenticated user's membership and returns 404 for non-members. `get_case_access` loads a case by both `case_id` and the authorized `workspace_id`; `get_document_access` then loads by both `document_id` and the authorized `case_id`. Direct IDs, cross-tenant requests, and any workspace/case/document mismatch therefore return 404 without revealing object existence.

For documents, OWNER, ADMIN, and MEMBER can upload, view, download, and archive; VIEWER can view and download. The API enforces the matrix independently of the UI.

### Private document storage boundary

```text
DocumentService -> StorageProvider -> LocalStorageProvider -> private Docker volume
```

The provider exposes staged writes, open, size, existence, and deletion primitives over opaque keys. Local storage generates temporary files beneath a private staging directory, fsyncs and atomically moves completed uploads, and resolves every key before access to prove it remains beneath `DOCUMENT_STORAGE_PATH`. Keys are UUID-derived as `workspace/case/document/stored-id`; original filenames remain metadata only. The abstraction can be replaced by S3, MinIO, or another object store without changing document records or nested API contracts.

Upload memory is bounded by 1 MiB chunks and `DOCUMENT_MAX_SIZE_BYTES` (50 MiB by default). SHA-256 is updated for each chunk. PDF and DOCX signatures/packages are validated from the staged original before publication. A storage failure produces no database row; a database failure after publication triggers object cleanup.

Documents have one `UPLOADED` lifecycle status in Phase 4. Archive sets `is_active=false` without deleting the database row or physical original. Archived originals remain downloadable by authorized members. Domain foreign keys use `RESTRICT`; no retention scheduler or permanent deletion exists.

## Current runtime

The API exposes `/health`, authentication under `/api/v1/auth`, workspaces and memberships under `/api/v1/workspaces`, cases nested beneath workspaces, and document operations nested beneath each case. PostgreSQL contains users, refresh sessions, workspaces, memberships, cases, and document metadata. The private document volume contains untouched original binaries and is not mounted into the frontend service.

The Document Vault UI lives at `/workspaces/:workspaceId/cases/:caseId/documents`. It calls only authenticated APIs and never receives a storage key or filesystem path.

Document text extraction and RAG are not part of Phase 4. OCR, chunking, embeddings, Qdrant indexing, LLM calls, chat, AI analysis, bitemporal logic, editing, replacement, and versioning remain intentionally absent.
